Reference migration pattern (established in `client/components/common/login-form/LoginForm.tsx`, repeated in `client/components/common/review-form/ReviewForm.tsx`): react-hook-form + zod + `@hookform/resolvers/zod`, with `useApiFormError` (`client/hooks/useApiFormError.ts`) feeding `useSyncApiFieldErrors` (`client/hooks/useSyncApiFieldErrors.ts`) which calls RHF's `setError` for server-side field errors.

**Why:** `simple-react-ui-kit`'s `Input`/`TextArea`/`Select`/`Checkbox` are plain `React.FC`, not `forwardRef` — `register()` doesn't work. Every field must be wrapped in `<Controller name="x" control={control} render={({field}) => <TextArea {...field} error={fieldState?.message ?? formErrors.x?.message} />} />`. Spreading `{...field}` (including `ref`) onto a non-forwardRef component is the accepted convention here (matches LoginForm) — it logs a harmless "function components cannot be given refs" warning, not a crash; don't try to "fix" this by inventing a different wiring, it's the established pattern.

**How to apply:**
- Custom non-kit controls (e.g. a clickable star-rating) also go through `Controller`, driven by `field.value`/`field.onChange` instead of local `useState`.
- To replicate an old hand-rolled `validate()`'s exact if/else-if branching (e.g. "required" must win over "too short" for an empty string, not report both), use `.superRefine((value, ctx) => { if (...) ctx.addIssue(...) else if (...) ... })` on that field's schema rather than chaining multiple `.min()`/`.max()` — chained checks can both fire for the same input and RHF only surfaces one, non-deterministically ordered from the chain.
- **Correction to the "correction" (verified 2026-08-19, by direct empirical test, not just reading test files):** the earlier note claiming `ProfileCard.tsx`/`ReviewForm.tsx` "still use `mode: 'onChange'` + `!isValid` gating" was **wrong** — it misread the files. As committed, both only gate their submit button on `isLoading || isSubmitting` (no `mode: 'onChange'`, no `isValid` in the destructure at all). The rule below is real and confirmed, not stale — do not repeat the mistake of "checking tests pass" as a proxy for "the UX is fine"; a disabled-with-zero-explanation button doesn't fail any assertion unless a test specifically renders a pristine form and asserts visible error text, which none of the affected forms' tests did.
- `mode: 'onChange'` + gating the submit button on `formState.isValid` is unsafe for any form with a field that starts invalid by default (i.e. any required field with no default value — which is every "create new X" form). Confirmed **twice** by direct render-and-inspect (not just reading test output): both `AstroObjectForm.tsx` and `AstroPhotoForm.tsx` shipped with this exact pattern, and a pristine `render(<Form />)` produced a permanently-disabled Save button with **zero visible error text anywhere in the DOM** — worse UX than the pre-migration code, which at least let you click Save. Root cause: with a schema resolver, RHF computes `formState.isValid` from the whole schema but only populates `formState.errors`/`fieldState.error` for fields the user has interacted with — an untouched-but-invalid field silently keeps `isValid` false forever with no rendered explanation. Fix applied to both: drop `mode: 'onChange'`, drop `isValid` from the destructure and from the disabled condition, gate only on `isSubmitting`/`isLoading` — first submit attempt then validates the whole schema and shows every error at once (RHF's default `mode: 'onSubmit'` + `reValidateMode: 'onChange'`). **This is the standing rule for every multi-field form in this migration — do not reintroduce `mode: 'onChange'` + `isValid` gating without first rendering a pristine (all-fields-empty) instance and confirming errors are visible, not just that the button eventually enables once every field happens to be filled by a test.**
- No new i18n keys needed if the migration keeps the exact same `t('key', 'fallback')` calls as the pre-migration file — check `public/locales/ru/translation.json` for the keys before assuming a locale edit is required.
- If the migration *does* introduce brand-new keys, run `yarn locales:build` (adds RU verbatim + an empty EN placeholder) then hand-fill the EN placeholder — but if a validation message's default text gets edited *after* the first `locales:build` pass (e.g. dropping `{{min}}`/`{{max}}` interpolation once real i18next resource files are found to override the JS-side default at runtime), both locale files keep the stale wording and must be hand-corrected too (same root cause as [[feedback_i18n_locale_build.md|i18n-locale-build-process]]'s "changing an existing key's default text does not auto-propagate" - just easier to hit mid-migration since the key is only minutes old). Prefer avoiding `{{}}` interpolation in a zod message entirely for a fixed numeric constant (hardcode the bound in the string) - simpler and there's no real translation-memory need for `.min(0, ...)`/`.max(360,...)`-style physical constants.
- `Select` (multi-select) has no `register()`/spreadable-field shape at all - its `onSelect` callback receives `Array<{key, value}> | undefined`, not a value/event. Wrap via `Controller` and adapt both directions manually: `value={field.value}` (an array for `multiple`) and `onSelect={(selected) => field.onChange(selected?.map(({key}) => key) ?? [])}`. Confirmed working in `AstroObjectForm.tsx`'s `categories` field (`client/components/pages/objects/astro-object-form/`) and matches the single-select `sex` field already in `ProfileCard.tsx`.
- For a numeric `Input` (`type="number"`) whose zod field is logically required (must reject empty), don't type the RHF field as `number | undefined` - the optional-vs-required generic mismatches make `useForm<T>`/`zodResolver<T>` fight each other. Instead keep the field type as plain `number` always, using `NaN` as the "empty" sentinel (exactly what `parseFloat('')` already produces): `defaultValues: { ra: NaN, ... }`, `onChange={(e) => field.onChange(parseFloat(e.target.value))}`, `value={Number.isNaN(field.value) ? '' : field.value}` (so the input doesn't literally display "NaN"). zod v4's `z.number({ error: '...' })` treats `NaN` as an `invalid_type` failure by default, so the custom `error` message doubles as the "required" message for free - no `.optional()`/`.refine()` gymnastics needed. Confirmed in `AstroObjectForm.tsx`'s `ra`/`dec` fields.
- **RHF's `handleSubmit(onValid)` always resolves the `onValid` call at least one microtask later than a plain hand-rolled async `onClick` handler**, even with a fully synchronous zod schema — `@hookform/resolvers/zod`'s resolver is itself always an `async` function. Migrating `EventBookingForm` (`client/components/pages/stargazing/event-upcoming/event-booking-form/EventBookingForm.tsx`) surfaced two consequences:
  - A `useEffect` that reacts to a mutation-hook flag (e.g. `isSuccess`) alongside a locally-`useState`-tracked "did we submit" flag (e.g. `submitted`) must list *both* in its dependency array, not just the mutation flag. The pre-migration handler set `submitted` synchronously as its very first line (before any `await`), so a test that changed `isSuccess` and re-rendered without awaiting the click would still see `submitted` already `true` by coincidence. Once `submitted` is set inside RHF's resolver-gated `onValid`, that synchronous guarantee is gone — the effect must re-run when `submitted` (or any other locally-set gating state, e.g. `paymentRedirect`) changes too, or a success arriving "too early" relative to the submit promise is silently missed forever.
  - Existing tests that do `fireEvent.click(submitButton); mock.mockReturnValue(...); rerender(...); await waitFor(...)` **without awaiting anything between the click and the rerender** are relying on exact microtask-ordering; the extra resolver hop can flip which state update "wins" the race. Prefer fixing the effect's deps (above) over trying to out-race the timing in the test.
  - Separately (not RHF-specific, but exposed by the above): `jest.clearAllMocks()` in a shared `beforeEach` does **not** clear a mock's `.mockResolvedValue(...)` from a previous test — only `mock.calls`/`instances` are cleared. A mutation mock used across multiple tests, some of which set a special resolved value (e.g. a paid-booking response with a payment redirect), needs an explicit baseline reset (`mockFn.mockReset().mockResolvedValue(defaultValue)`) in `beforeEach`, or a later test can silently inherit an earlier test's response shape.
- **`useFieldArray` is the right tool for a dynamic list of sub-objects** (confirmed in `AstroPhotoForm.tsx`'s `filters` field, `client/components/pages/photos/astro-photo-form/`, replacing separate `selectedFilter`/`addedFilters` `useState`s + a keyed `Record<FilterType, Statistic>`): model it as `filters: Array<{ filter: FilterTypes; frames: number; exposure: number }>` in RHF's form values, `useFieldArray({ control, name: 'filters' })`, and only convert to/from the external keyed-object shape (`Record<FilterType, Statistic>`) at the two boundaries — inside `reset()` when `initialData` arrives, and inside the submit handler right before calling the parent's `onSubmit`. Nested field errors address as `` `filters.${index}.frames` `` in both the `Controller name` and (if the backend ever returns them) the server field-error key.
  - `append()`/`remove()` DO trigger a full-schema revalidation even without `mode: 'onChange'` and even though nothing in the newly-appended row has fired a `change` event — a schema-based resolver always re-validates the whole `values` object, not a single field. This is irrelevant to the `isValid`-gating question above (still don't gate the button on it) but matters for catching a `NaN`-sentinel row at actual submit time: `AstroPhotoForm.tsx` relies on this to reject an added-but-never-touched filter row when the user clicks Save, via the array's own `.min(1, ...)` plus per-item `frames`/`exposure` checks in the schema.
  - zod v4's `z.enum()` wants a non-empty tuple type (`[T, ...T[]]`), not a plain `T[]`. When the allowed values come from a runtime `Object.keys(...)` (e.g. `ApiModel.filters`), cast: `z.enum(FILTER_KEYS as [ApiModel.FilterTypes, ...ApiModel.FilterTypes[]])` — safe here since the source object is a fixed non-empty const, just not provably so to TS.
- **A full `yarn jest --coverage=false` run (all suites) can be flaky in this sandbox under default (parallel-worker) settings** — observed 2026-08-19: a run right after `yarn locales:build` showed 11 failures across 4 unrelated suites (`LoginForm`, `AstroObjectForm`, `ProfileCard`, `AstroPhotoForm`), all `waitFor(...)` timeouts on zod-validation-driven UI updates; re-running the identical command with `--runInBand` (single worker, no cross-process CPU contention) passed all 272 tests immediately, and a subsequent default parallel run came back clean too. Root cause looks like CPU contention between worker processes in this environment, not a real bug — locale-file content was independently verified unchanged for the affected keys. **When a full-suite run shows scattered timeout failures in files you didn't touch, re-run with `--runInBand` before concluding something is actually broken.**
- **The shared Jest manual mock (`client/__mocks__/simple-react-ui-kit.tsx`) originally had `Select` render only its `label`, dropping `error` entirely** (unlike its `Input`/`TextArea`, which already rendered `{error && <span>{error}</span>}`) — any form relying on this shared mock (rather than an inline per-test `jest.mock('simple-react-ui-kit', ...)`) could never assert a `Select`/multi-select validation error was visible, even when the component correctly passed `error` through. Fixed by adding the same `{error && <span>{error}</span>}` line to the shared mock's `Select`. If a form-level test can't find an expected `Select` error message, check whether the shared mock actually renders `error` before assuming the component itself is broken.
- **Running `yarn locales:build` scans the *entire* codebase, not just the file you're migrating** — if other files in the working tree already have new/uncommitted `t('key', 'fallback')` calls that were never built yet (common when several forms are mid-migration in parallel), the same `locales:build` invocation will pick up *all* of them, producing a much bigger `public/locales/*/translation.json` diff than your own change. This is expected/correct behavior (the generator is supposed to keep the whole file in sync), not scope creep introduced by your edit — but call it out explicitly when reporting your diff so it isn't mistaken for unrelated changes you made by hand.
