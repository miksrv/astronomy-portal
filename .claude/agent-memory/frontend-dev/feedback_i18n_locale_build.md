description: How translation keys are managed — scanner reads source files; do not edit locale JSON directly; changing an existing key's default text does NOT auto-propagate
type: feedback
---

Translation keys are auto-generated by `yarn locales:build` (runs `i18next-scanner`). The scanner reads `t('key', 'default')` calls from all `.ts`/`.tsx` files and updates `/public/locales/{ru,en}/translation.json`. `removeUnusedKeys: true` is set, so keys with no remaining `t(...)` call anywhere in source are pruned from both files on the next build.

**Why:** `i18next-scanner.config.js` has a custom `flush` that snapshots both `en/translation.json` and `ru/translation.json` at module-load time, then for every key merges: if the snapshot already has a **non-empty string** for that key, the snapshot value wins outright — for both languages, not just EN. This preserves hand-corrected plural forms the scanner can't derive from a single source string. The `fallbackToScanned` flag (true for ru, false for en) only decides what happens when the snapshot has **no** value at all (a brand-new key): ru falls back to the freshly-scanned Russian source text, en falls back to `""`.

**Corrected misconception:** RU is *not* "always written verbatim from the scanner." **Verified 2026-08-14** by changing an existing key's default RU text in source (`components.pages.index.main-sections.event-photo-alt`) and running the build — the RU file kept the *old* stale text, exactly like EN did. Only brand-new keys get the fresh scanned text for RU.

**How to apply:**
- Add `t('key', 'Russian default')` in source, then run `yarn locales:build`.
  - Brand-new key → RU gets the scanned Russian text automatically; EN gets `""` and needs manual translation.
  - Existing key whose default text you just *changed* in source → **neither** locale file updates automatically; you must hand-edit both `ru/translation.json` (to match the new source default) and `en/translation.json` (to a corresponding English translation) after running the build.
- To add an English translation for a new key: edit `en/translation.json` directly (fill in the `""` value), then running `yarn locales:build` again preserves it (non-empty snapshot wins).
- After any `locales:build` run, grep both files for empty-string values (`python3` one-liner walking the JSON works well) to catch every key needing manual translation — this also surfaces pre-existing empty/missing EN keys left over from a previous change that skipped running the build, which are worth fixing in the same pass rather than leaving them broken.
- Never hand-edit `ru/translation.json` casually assuming it'll be regenerated correctly from source on the next build — for any key that already exists in the file, it won't be.
